## Verification and custom Python


<a id="g01"></a>
### G01 — Unresolved exact-division verification counterexample

**Priority:** P0.

The retained numerator `0x8147ec48` and denominator `0x21dea823` produce `0x9ee5dc9c` in the SASS emulator versus `0x9ee5dc9d` in the PTX interpreter. Baseline and post-repair records agree: saturation/FTZ fixes did not resolve this one-ULP discrepancy. MUFU and FCHK still contain approximate or hypothesis-based models. This is an unresolved verification-model issue; it is not evidence that the current native GPU division result is wrong. A random suite pass cannot supersede the fixed counterexample.

**What closes this gap:** Replay the exact inputs and emitted sequence on hardware against an independent exact reference, isolate approximation/slow-path/rounding behavior, and retain a deterministic regression before changing verification status.

**Evidence:** [docs/compiler/semantic-acceptance.md](/Users/lucasfang/Desktop/OpenAssembler/docs/compiler/semantic-acceptance.md:140); [compiler_exp/semantic_acceptance/emulator-limit-current.json](/Users/lucasfang/Desktop/OpenAssembler/compiler_exp/semantic_acceptance/emulator-limit-current.json); [openassembler/emu/ops.py](/Users/lucasfang/Desktop/OpenAssembler/openassembler/emu/ops.py:1033).


<a id="g02"></a>
### G02 — Full semantic conformance is still a larger task than scalar admission

**Priority:** P1.

The new scalar admission schema and 426 recorded forms are valuable repairs. They enumerate admissible modifier/type/arity shapes, not 426 fully supported and hardware-proven operations. Later selection, operand restrictions, register allocation and encoding can still reject; tensor instructions have a separate checker. For example, vector-two global loads appear in the schema but the selector rejects them. Syntax acceptance, encoded words, packaged cubin, hardware correctness and speed are separate evidence levels.

**What closes this gap:** Maintain one machine-readable cross-stage contract ledger with exact forms, supported operand domains, rejection reasons and independent CPU/toolkit/hardware evidence. Cover combinations and negative controls, rather than counting mnemonics or parser acceptance.

**Evidence:** [openassembler/backend/contracts.py](/Users/lucasfang/Desktop/OpenAssembler/openassembler/backend/contracts.py:18); [openassembler/backend/ra.py](/Users/lucasfang/Desktop/OpenAssembler/openassembler/backend/ra.py:656); [docs/compiler/semantic-acceptance.md](/Users/lucasfang/Desktop/OpenAssembler/docs/compiler/semantic-acceptance.md:50).


<a id="g03"></a>
### G03 — Custom Python types and numerical semantics remain narrow

**Priority:** P1.

The kernel language exposes only `i32`, `u32`, `f32` and arrays of those elements. It lacks user-facing half/BF16/FP64, wider integer and general Boolean/vector types. Python unbounded integers become wrapping 32-bit values and Python float64 arithmetic becomes FP32 arithmetic. Division-by-zero, conversion and negative-index behavior do not become ordinary Python exceptions. Exp/log/tanh/rsqrt are declared approximate intrinsics. Thus accepting Python syntax does not establish arbitrary Python semantics or generic mixed precision.

**What closes this gap:** Define the intended typed device-language contract, implement missing types and conversions end to end, and test overflow, rounding, exceptional values and math policies independently. Keep strict FP32, approximate math and half-rounded products distinct.

**Evidence:** [openassembler/pyfront/types.py](/Users/lucasfang/Desktop/OpenAssembler/openassembler/pyfront/types.py:22); [openassembler/pyfront/compile.py](/Users/lucasfang/Desktop/OpenAssembler/openassembler/pyfront/compile.py:17).


<a id="g04"></a>
### G04 — Reusable Python functions and library calls are not generally compilable

**Priority:** P1.

Static compilation finds top-level `@kernel` functions and resolves a small intrinsic/import vocabulary. Arbitrary user helper calls, recursion, nested functions, lambdas and general NumPy/Python/package methods do not lower. This blocks factoring custom kernels into reusable device libraries, even when the intended computation is numeric and otherwise GPU-compatible. Import statements used for name resolution are not a package compiler or a device linker.

**What closes this gap:** Add typed device-function specialization or inlining with explicit call signatures, captured constants, effect rules and source locations; support separate device calls only with a valid ABI. Test multi-module helpers without executing arbitrary top-level host code during static discovery.

**Evidence:** [openassembler/pyfront/compile.py](/Users/lucasfang/Desktop/OpenAssembler/openassembler/pyfront/compile.py:976); [openassembler/pyfront/compile.py](/Users/lucasfang/Desktop/OpenAssembler/openassembler/pyfront/compile.py:100); [openassembler/pyfront/compile.py](/Users/lucasfang/Desktop/OpenAssembler/openassembler/pyfront/compile.py:1279).


<a id="g05"></a>
### G05 — Python objects, containers and compile-time programming lack a general route

**Priority:** P1.

Lists, tuples/dicts as kernel values, strings, arbitrary attributes, comprehensions, classes, generators, exceptions and context managers are outside the numeric kernel subset. There is no general compile-time tensor/block DSL, Python object specialization or runtime object model. These restrictions affect practical parameterized custom kernels as well as arbitrary Python. Host-side objects and I/O also require a preserved host runtime, not just SASS generation.

**What closes this gap:** Separate compile-time values, host-only effects and device values; admit useful static containers/constants and metaprogramming under explicit specialization rules. Preserve host effects through the application route rather than silently deleting them.

**Evidence:** [openassembler/pyfront/compile.py](/Users/lucasfang/Desktop/OpenAssembler/openassembler/pyfront/compile.py:100); [openassembler/pyfront/compile.py](/Users/lucasfang/Desktop/OpenAssembler/openassembler/pyfront/compile.py:727).


<a id="g06"></a>
### G06 — Python control flow is useful but not unrestricted

**Priority:** P1.

Data-dependent `if` and `while`, nested `range` loops, break and continue already exist; they should not be listed as wholly missing. Remaining restrictions include iteration over arbitrary iterables, nonconstant range steps, for/while-else, chained comparisons, first-class Boolean expressions and returned device values. Fixed-width loop counters can wrap. General Python execution and efficient lowering of arbitrary control-flow graphs remain outside the contract.

**What closes this gap:** Extend only declared control-flow forms with branch/loop state semantics, defined overflow behavior and convergence checks. Test nested loops, early exits, loop-carried values and long-running bounds through encoding and hardware.

**Evidence:** [openassembler/pyfront/compile.py](/Users/lucasfang/Desktop/OpenAssembler/openassembler/pyfront/compile.py:548); [openassembler/pyfront/compile.py](/Users/lucasfang/Desktop/OpenAssembler/openassembler/pyfront/compile.py:622); [openassembler/pyfront/compile.py](/Users/lucasfang/Desktop/OpenAssembler/openassembler/pyfront/compile.py:79).


<a id="g07"></a>
### G07 — Custom-kernel arrays have no general tensor/view/layout API

**Priority:** P1.

`Array(TYPE)` is a flat pointer, indexed with 32-bit expressions. Shapes, strides, buffer lengths, alignment promises and ownership are not rich type-level contracts. Multidimensional layout arithmetic can be written manually, but there is no general tensor slicing/view/broadcast interface or block load/store masking abstraction. This makes arbitrary custom tensor kernels harder to express, verify and optimize, even when scalar indexing itself works.

**What closes this gap:** Introduce explicit buffer/shape/stride/alignment and alias contracts, including safe masks and tails. Validate negative/runtime indices, offset overflow, views and external tensor bindings; exploit those facts for code generation without assuming contiguity.

**Evidence:** [openassembler/pyfront/types.py](/Users/lucasfang/Desktop/OpenAssembler/openassembler/pyfront/types.py:18); [openassembler/pyfront/compile.py](/Users/lucasfang/Desktop/OpenAssembler/openassembler/pyfront/compile.py:86).


<a id="g08"></a>
### G08 — Python GPU primitive vocabulary is incomplete

**Priority:** P1.

Python intrinsics cover thread/block coordinates, selected math, static shared arrays and `syncthreads`. They do not expose general atomics, warp votes/shuffles/reductions, asynchronous copies, device calls or tensor instructions as a complete custom-kernel language. Low-level backend support would not automatically make those facilities available from Python; conversely, adding intrinsic names without backend semantics would not add coverage.

**What closes this gap:** Connect a typed primitive vocabulary to complete PTX/native contracts, including mask, scope, ordering, synchronization and collective participation rules. Test the Python-to-binary path for every admitted primitive.

**Evidence:** [openassembler/pyfront/intrinsics.py](/Users/lucasfang/Desktop/OpenAssembler/openassembler/pyfront/intrinsics.py); [openassembler/pyfront/__init__.py](/Users/lucasfang/Desktop/OpenAssembler/openassembler/pyfront/__init__.py:38).


<a id="g09"></a>
### G09 — Memory safety and shared-memory initialization checks are incomplete

**Priority:** P1.

The recent no-possible-writer shared-read check closes one real bug class. It does not prove that a writer runs before a read, that threads synchronize correctly, or that every branch initializes a slot. General runtime global/shared bounds instrumentation, alias/race analysis and convergence proof remain absent. Static shared arrays are literal-sized, top-level allocations capped at 48 KiB in this Python frontend. Finite canary tests cannot establish safety for all future inputs.

**What closes this gap:** Declare unsafe versus checked execution; add useful definite-initialization, bounds and synchronization analyses or diagnostics. Use adversarial schedules, masks, dimensions and hardware checking, while preserving explicit rejection where safety cannot be established.

**Evidence:** [docs/compiler/semantic-acceptance.md](/Users/lucasfang/Desktop/OpenAssembler/docs/compiler/semantic-acceptance.md:80); [openassembler/pyfront/compile.py](/Users/lucasfang/Desktop/OpenAssembler/openassembler/pyfront/compile.py:136); [openassembler/pyfront/compile.py](/Users/lucasfang/Desktop/OpenAssembler/openassembler/pyfront/compile.py:1181).


## PTX, CUDA and native backend


<a id="g10"></a>
### G10 — PTX parameter ABI and module grammar are bounded

**Priority:** P1.

Bare/visible/weak entry discovery, entry inventories and selected launch directives are repaired. ### G12 — Global/shared memory widths and vector forms remain uneven

**Priority:** P1.

### G13 — Address spaces and module storage are not generally lowered

**Priority:** P1.

Global/shared pointers and kernel parameters cover current generated kernels. General local-memory accesses, constant-memory symbols, initialized global/module data and their symbol/address relocation semantics are not a complete backend facility. Parsing a storage declaration or emulating it is not the same as placing it correctly in an executable module. ### G14 — Atomics, reductions and memory ordering are missing compiler foundations

**Priority:** P1.

Global atomic add/CAS, reduction instructions, fences and acquire/release/volatile contracts are still rejected by the production path. ### G15 — Warp/block collective and synchronization support is narrow

**Priority:** P1.

The native scalar path handles a specific full-mask, unpredicated butterfly shuffle and block barrier 0. General indexed/up/down shuffles, partial masks, votes/ballots, match/redux, additional barrier forms and broader cooperative synchronization do not form a general supported set. Current row kernels carefully fit the admitted full-warp/tail discipline. Arbitrary custom kernels may have different participant and divergence requirements.

**What closes this gap:** Add collective participation and mask semantics alongside encoding and scheduling. Validate partial warps, divergent control flow, all barrier participants and memory visibility independently on hardware.

### G16 — Device calls, call stacks and cross-module device linking are absent

**Priority:** P1.

The backend is entry-local; a PTX device-function call rejects. There is no general device-call ABI, return-value/parameter convention, stack frame, recursive call support or device linker resolving functions across translation units/libraries. nvcc can inline some helpers before OA sees them, but this does not establish support for calls that survive. Separate cubins and donor relocations do not constitute whole-program device linking.

**What closes this gap:** Implement a defined call ABI or bounded whole-program inlining/specialization, symbol resolution and stack/local allocation. Test multiple translation units, library calls, recursion policy and resource accounting.

### G17 — Register/predicate spilling and general pressure management are missing

**Priority:** P1.

### G19 — Native GPU architecture coverage remains SM80/A100

**Priority:** Separate target.

SM86 and SM90 probes still reject for missing encoder data; tensor generation explicitly requires SM80, and native model execution requires an A100-compatible contract. ## Model language and tensor semantics


<a id="g21"></a>
### G21 — Framework operator coverage is still a small whitelist

**Priority:** P1.

FX capture now includes bounded embedding and SDPA as well as Linear, ReLU, tanh GELU, softmax, LayerNorm, layout/concat, add/mul and products. It still rejects common operations such as convolution, pooling, sigmoid, general sum/reductions, division, slicing/indexing and exact GELU. There is no general normalized ATen/export/decomposition/dispatch route covering arbitrary ML workloads. Implementing one operator spelling also does not automatically cover equivalent method/custom-module forms.

**What closes this gap:** Build a normalized operator/effect IR with generic faithful lowerings and derivatives, then add optimized recipes. Admit independent CNN, recurrent, transformer, indexing and scientific workloads through the same normal entrypoints.

### G22 — Model control flow and shapes are static specializations

**Priority:** P1.

Capture uses CPU FX tracing and exact example shapes. Tensor-dependent Python branching, symbolic shapes and general dynamically generated graph structure are not supported. The custom Python kernel language having `while` does not make an arbitrary model training loop capturable. Changing sequence/batch lengths needs already compiled contracts or a new explicit build; there is no general guard/recompile/lazy OA specialization policy.

**What closes this gap:** Define shape/effect guards, guard-miss behavior and bounded AOT or explicit lazy specialization. Preserve host control flow where appropriate and test unseen values, lengths, branches and recompile/cache behavior.

<a id="g23"></a>
### G23 — Model storage/dtype and AMP coverage remain restricted

**Priority:** P1.

Weights, arithmetic and gradients remain FP32. External int64 indices and Boolean masks are now admitted for specific operations, but do not provide general integer/Boolean tensor computation. True FP16/BF16/FP64 model storage, quantized/complex types, automatic mixed precision and loss scaling are not general model contracts. Low-level BF16 MMA support is separate. The half-rounded product option retains FP32 storage and declares a straight-through cast policy in backward; it is not interchangeable with generic AMP.

**What closes this gap:** Specify dtype promotion, accumulation, cast derivatives, master state and overflow policies end to end. Compare complete training states under the identical policy, including exceptional and small-gradient cases.

### G24 — Arbitrary strides, aliases and mutation effects are unsupported

**Priority:** P1.

Inputs/state must be contiguous and exact shape; distinct overlapping state tensors reject. Supported reshape aliases and view/reuse planning are not a general alias/effect system. Tensor slices, arbitrary strided views, in-place ReLU/out= mutation and state mutation during capture reject. Supported permutations may materialize copies. A model using shared mutable views, rolling buffers or channels-last layouts therefore needs more than an operator name addition.

**What closes this gap:** Track base storage, offsets, strides, alias sets and mutation/version effects through capture, differentiation, planning and execution. Test overlapping views, state updates, storage reuse and backward saved-value lifetimes.

### G25 — Broadcast support is partial and does not extend to batched matmul

**Priority:** P1.

Trailing-axis FP32 add/mul broadcasting with reduction-correct backward now works through rank four, including scalar tensors. That closes the previous bias-broadcast gap. **What closes this gap:** Extend broadcasting as an explicit shape/layout algebra per operation, including inverse gradient reductions and batch products. Validate rank, scalar, singleton and noncontiguous cases without silently expanding precision or storage contracts.

### G26 — Hard resource bounds exclude common large ML shapes

**Priority:** P1.

The supported Torch range is pinned, not arbitrary installed versions.

## Efficiency, measurements and evidence


<a id="g45"></a>
### G45 — General scheduling, tiling and cost models remain incomplete

**Priority:** P2.

Measured scheduling, protected tensor controls and exact GEMM/rowwise/model policies improve selected cases. They do not supply a shape/layout/architecture-general optimizer balancing coalescing, address work, register pressure, occupancy, reuse, copy overlap and fusion. More buffers or earlier loads can lose through pressure; larger occupancy alone is not a speedup. Unknown contracts deliberately retain baseline policies. Exact table counts measure admitted tuning cases, not universal kernel coverage.

**What closes this gap:** Use legal candidate generation with resource/dependency models, independent correctness gates and frozen held-out selection. Optimize real workload distributions and compare both the incumbent and named external controls.

**Evidence:** [openassembler/backend/tensor.py](/Users/lucasfang/Desktop/OpenAssembler/openassembler/backend/tensor.py:29); [openassembler/kernels/gemm.py](/Users/lucasfang/Desktop/OpenAssembler/openassembler/kernels/gemm.py:18); [docs/compiler/memory-latency.md](/Users/lucasfang/Desktop/OpenAssembler/docs/compiler/memory-latency.md:13).


<a id="g46"></a>
### G46 — Whole-model fusion, packing and launch planning remain limited

**Priority:** P2.

Recent exact small-product and reduction improvements are real but retain explicit shape guards. General producer/consumer fusion, eliminating repeated transpose/round/pack/crop work, layout propagation and joint forward/backward launch planning remain opportunities. FP32 products often use scalar/tiled paths, and half recipes incur packing/padding. New broadcast, attention, embedding and optimizer kernels add composition costs that isolated GEMM or fixed-coefficient timings do not capture.

**What closes this gap:** Compare complete pack+compute+crop and forward/backward/update regions with exact liveness/precision/effect rules. Reduce allocations/traffic/launches only after all storage-view/reuse, changed-input and full-state gates pass.

**Evidence:** [openassembler/modelfront/kernels_tensor.py](/Users/lucasfang/Desktop/OpenAssembler/openassembler/modelfront/kernels_tensor.py:87); [openassembler/modelfront/tensor_schedule.py](/Users/lucasfang/Desktop/OpenAssembler/openassembler/modelfront/tensor_schedule.py:6); [exp/model_perf/RESULTS.md](/Users/lucasfang/Desktop/OpenAssembler/exp/model_perf/RESULTS.md:121).


<a id="g47"></a>
### G47 — Cold/warm compilation and cache-hit overhead lack complete attribution

**Priority:** P2.

The model worker now reports CPU factory, capture/autodiff, storage planning and native bundle/weights times. Backend emission, ptxas, packaging, disassembly and cache validation remain aggregated inside bundle work; independent repository sources and transport/validation are excluded from those four phases. Cached builds still regenerate/validate source and plan identity, which can dominate small builds. Correct binary-only nvdisasm independence does not establish fast cache hits.

**What closes this gap:** Record nonoverlapping frontend/PTX/backend/ptxas/container/disassembly/cache/source/archive/startup/transfer phases for clean and validated warm builds. Preserve raw samples and distinguish remote waiting from compiler time.

### G48 — Standard reports lack per-kernel steady-state distributions

**Priority:** P2.

Existing reports retain host step and stream elapsed samples, ledgers, profiler audits and zero-vendor-compute fields. That does not give repeated distributions for every unique kernel contract or attribute host validation/transfers/packing consistently. ### G49 — Full-workload comparisons and compile amortization remain incomplete

**Priority:** P2.

The November 19 model campaign improved OA over its frozen incumbent, while fresh direct Triton and same-PTX ptxas controls remained faster on its three tasks. ## Practical consequences for workload families

| Intended workload | Current useful starting point | First likely remaining blockers |
|---|---|---|
| Handwritten elementwise/reduction Python kernel | Typed @kernel, scalar control flow and shared arrays | Device helper reuse, types/layouts/masks, missing primitives and unchecked dynamic memory accesses. |
| Numeric Python kernels with package abstractions | Static import/name resolution | Objects/metaprogramming/functions plus faithful device library lowering. |
| CUDA extension with scatter/reduction/device helpers | nvcc-to-PTX plus OA entry compilation | Atomics/order, ABI, calls/linking/spills, build integration and host launch bindings. |
| CNN inference/training | Bounded model factory/FX route | Convolution/pooling and related operator/state/dtype coverage. |
| Small FP32 token model | Embedding + causal SDPA + CE/AdamW example | Restricted options/shapes, direct dispatch, host index checks and scalable embedding/attention. |
| Larger language model training | Existing transformer components and exact matrix recipes | Vocabulary/classes >1024, context/element/half-BMM caps, mixed precision, RNG, sharding and memory traffic. |
| Token-by-token serving | Owned prefill/decode session | Precompiled length coverage, cache copies/paging, batching/concurrency and complete serving validation. |
| Higher-order/differentiable optimizer workload | First-order symbolic model gradients | Higher-order autograd, custom backward/update effects and retained tape semantics. |

This table predicts likely boundaries from explicit source contracts. It is not a claim that every representative third-party repository was executed.

## Recommended delivery order and exit gates

1. **Stabilize the verification and support ledger:** resolve G01 against hardware; retain the repaired saturation/FTZ gates; reconcile full form admission versus actual lowering; fix stale capability tests without weakening numerical gates.
2. **Make custom Python kernels practical:** typed reusable helpers, richer buffer/layout contracts, missing useful types and primitives, then the device foundations those need—memory widths, atomics/order, calls/linkage and spills. Preserve a clear host/device boundary.
3. **Finish normalized ML semantics:** operator coverage, layouts/effects/RNG, dtype policy, scalable shape admission, embedding/attention/loss variants and optimizer options. Keep already implemented bounded features visible rather than restarting them.
4. **Integrate real applications and dynamic state:** original builds/dependencies and custom-op launches, complete checkpoint/host behavior, cache length/memory policies and explicit dynamic specialization. Select independent real CNN, transformer and custom-extension applications.
5. **Generalize efficiency with complete measurements:** legal scheduling/layout/fusion/packing candidates, full-state gates, randomized paired timings and held-out confirmation. Include compile/cache/startup/host/bounds checks/transfers and amortization. Add targets/toolchain independence as separately scoped projects.

Every completion claim should name exact shapes/strides, dtype/math policy, loss/optimizer options, RNG/effects, resource domain, architecture and dependency versions. Preserve source/config/plan/kernel/binary identities, all output and state comparisons, launch-ledger/profiler ownership and explicit unsupported/skipped/failed/not-run rows. A candidate only becomes a performance result after its correctness gate passes.

For comparisons, use identical PTX for OA versus ptxas; identical model/workload semantics for Triton/Inductor/eager; matching matrix contracts for cuBLAS/cuBLASLt with tuning disclosed. Report named comparator/OA ratios (>1 means OA faster) and `build_time + startup_time + N * steady_state_time`. Do not combine different A100 variants or toolchains, and do not turn unsupported cases into slow timing values.
